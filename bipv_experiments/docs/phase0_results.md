# Phase 0 결과 보고: TiDE가 태양추적보다 나쁜 원인 분해

- 작성일: 2026-10-04
- 대상 모델: `case_idf/case3_v3_KS/case3_v3_south.idf` (South BIPV, 10분 간격, 연간)
- Net energy 정의: `냉방/3.0 + 난방/2.5 − PV 발전량` (kWh, Ideal Loads 열부하 기준)

## 1. 배경 — 왜 Phase 0을 했나

### 1.1 문제
`fig38_1`에서 TiDE가 고른 각도 스케줄의 연간 net energy가 **태양 고도 추적 baseline보다 높게** 나왔다.

| | 태양추적 | TiDE S1 (당시) | TiDE S2 |
|---|---|---|---|
| 연간 Net (kWh) | −4,658 | −4,463 | −3,606 |

### 1.2 사용자 가설
> 특정 시점의 net energy는 이전 시간의 영향(열적 관성)을 받는데, 모델은 그 timestep의 net energy만 보고 각도를 고른다.
> 그래서 그렇게 뽑은 각도를 이어 붙여 시뮬레이션하면 net energy가 최소가 되지 않는다.

### 1.3 코드 조사에서 발견한 다른 의심 원인
가설 외에도 다음 문제가 동시에 존재했다.

1. **학습/배포 모델 불일치**
   - TiDE 학습: case2 (`case_idf/case2_KS/case2_{각도}.idf`). 그림자 계산 30일 주기, 각도별 단일 형상.
   - 실제 적용: case3. 매 timestep 그림자 계산, 10개 각도 형상을 투과율 액추에이터로 전환.
2. **라벨 오염**: augmented 데이터셋에서 고정각 채널 일부를 case3 태양추적 결과로 덮어씀.
3. **평가 신뢰성**
   - fig38_1의 S1 막대는 재학습 이전 체크포인트로 돌린 결과였다.
   - `case3_v3_south.idf`의 PythonPlugin 모듈이 `model_pythonpluginsystem_sun_tracking`으로 바뀌어 있었다. 재실행하면 TiDE가 아니라 태양추적이 돌아갈 위험이 있었다.

### 1.4 Phase 0의 목적
원인이 "**결정 방식(timestep 단위 argmin)이 근본적으로 틀렸는가**" 아니면 "**예측이 틀렸는가**"를 시뮬레이션으로 분리하는 것.

핵심 실험은 **Oracle-in-the-loop** 이다.

1. case3로 고정각(0°~90°) 연간 시뮬레이션 10개를 돌린다.
2. 각 timestep에서 net이 가장 작은 각도를 "정답"으로 골라 스케줄(oracle)을 만든다.
   - 예측 오차가 0인 완벽한 TiDE가 낼 수 있는 스케줄이다.
3. 이 스케줄을 실제 EnergyPlus에 넣어 돌린다.

결과 해석 기준:
- **oracle도 태양추적에 지면** → timestep 단위 결정 자체가 문제 (가설이 주원인).
- **oracle은 이기는데 TiDE가 지면** → 예측 오차 / 학습 데이터 불일치가 주원인.

검증: 2일 스모크 테스트에서 고정 0° run은 0° 발전기만, 태양추적 run은 1월 태양고도에 맞는 10°·20°·30° 발전기만 발전 → 스케줄이 정확히 적용됨을 확인.

### 2.2 실행한 시뮬레이션 (총 15개, 모두 0 Severe Errors)

| 그룹 | run | 스케줄 파일 (`data/schedules/`) |
|---|---|---|
| 고정각 | `fixed_A00` ~ `fixed_A90` (10개) | `fixed_AXX.csv` |
| baseline | `suntracking_w0s90` | `suntracking_w0s90.csv` (낮: 태양고도 최근접 10° 단위, 밤: 11~3월 0°, 그 외 90°) |
| 현재 TiDE | `tide_s1_current`, `tide_s2_current` | 현재 체크포인트로 만든 S1/S2 스케줄 |
| oracle | `oracle_stepwise` | timestep별 net 최소 각도 |
| oracle | `oracle_pvmax` | timestep별 PV 최대 각도 |

- 결과 위치: `case_analysis/case3_schedule_runs/<run>/` (`eplusout.sql`, `case3_south_tide_annual_summary.json`)
- 소요 시간: 연간 1회 약 12~20시간. 13개 동시 실행 시 약 22시간 → **병렬 실행해도 1개 실행과 시간이 비슷**하다.

> 각도 정의: tilt = 90° − angle. 즉 **0° = 패널 수직**, **90° = 패널 수평**.

> **"case3 고정각"의 의미**
> - case3 IDF는 10개 각도(0°~90°)의 차양·PV 형상을 모두 갖고 있다. 매 timestep 어느 각도를 켤지는 Python 플러그인이 정한다.
> - 태양추적형이라는 것은 건물이 아니라 원래 연결된 플러그인(`model_pythonpluginsystem_sun_tracking.py`)의 규칙이다.
> - 이번에는 플러그인을 CSV 재생형(`model_pythonpluginsystem_ai.py`)으로 바꿨다. 따라서 `fixed_A50` 같은 run은 **같은 case3 건물에서 1년 내내 50° 형상만 켜고 운전한 시뮬레이션**이다.
> - 이 방식으로 태양추적 스케줄을 재실행한 결과(−4,658.4 kWh)가 원래 case3 태양추적 결과와 소수점까지 일치했다.
> - case2는 이와 달리 각도마다 별도 IDF(형상 1개)를 쓰는 다른 모델이다.

### 3.2 핵심 실험 1 — Oracle-in-the-loop

| | Net (kWh) |
|---|---:|
| oracle, 고정각 결과를 이어 붙인 오프라인 추정 | −8,728 |
| oracle, **실제 EnergyPlus 실행** | **−7,624** |
| 태양추적 | −4,658 |
| TiDE S1 / S2 | −3,474 / −3,607 |

- **예측이 정확하면 timestep 단위 결정만으로도 태양추적보다 약 2,970 kWh(64%) 좋다.**
- 오프라인 추정과 실제 실행의 차이 **약 1,100 kWh**가 시간 누적(열적 관성) 효과의 크기다.

→ **판정: TiDE가 진 주원인은 결정 방식이 아니라 예측 오차다.** 사용자 가설(관성)은 실제로 존재하지만, 크기는 추가 개선 여지(~1,100 kWh) 수준이다.

### 3.3 핵심 실험 2 — 시간 누적 효과는 어디에서 생기나 (Stitch 비교)
같은 스케줄에 대해 두 값을 비교했다.
- (a) 고정각 결과에서 그 timestep 각도의 값을 골라 합한 값 (stitch)
- (b) 그 스케줄로 실제 동적 실행한 값 (E+)

차이가 0이면 그 항목은 "그 순간의 각도만으로 결정"되고, 차이가 크면 "과거 각도 이력의 영향"을 받는다.

| 스케줄 | PV 차이 | 난방 차이 | 냉방 차이 | Net 차이 |
|---|---:|---:|---:|---:|
| 태양추적 | **0** | **+3,104** | −90 | +1,211 |
| TiDE S1 | 0 | +1,022 | −359 | +289 |
| TiDE S2 | 0 | −673 | −665 | −491 |
| oracle_stepwise | 0 | +2,755 | +7 | +1,104 |

(차이 = E+ − stitch, kWh)

- **PV: 시간 누적 효과 없음.** 모든 스케줄에서 정확히 일치한다.
- **난방: 과거 이력에 강하게 의존한다** (최대 약 3,100 kWh).
- 냉방: 영향이 작다.

→ **TiDE가 태양추적보다 PV를 약 1,100 kWh 덜 생산한 것은 관성과 무관한 순수 예측 오류**다. case2로 학습한 모델이 case3의 PV(그림자 계산 방식 차이 등)를 잘못 예측한 것으로 판단된다.

### 3.4 oracle은 어떻게 이겼나 — 각도 선택 패턴

| 구간 | oracle이 고른 각도 |
|---|---|
| 난방 중 · 야간 | 0° (100%) |
| 난방 중 · 주간 | 0° 72%, 60° 11%, 50° 9%, 40° 5% |
| 난방 없음 · 주간 | 60° 55%, 50° 15%, 40° 9%, 70° 6% |

- **난방이 필요한 시간에는 패널을 0°(수직)로** 세워 난방을 줄였다. 연간 난방 38,066 → 31,790 kWh, 약 6,300 kWh 감소.
- **그 외 시간에는 PV 최대화**(주로 60°)를 했다.
- 고정각별 야간 난방도 0°가 12,677 kWh, 나머지는 약 14,300~15,100 kWh로 차이가 난다.
  → 기존 결론("야간 각도는 EnergyPlus에서 효과 없음")과 달리, **겨울 야간 각도는 난방에 영향이 있다.**
- 0°에서 난방이 줄어드는 물리적 메커니즘(창 앞 수직 패널에 의한 하늘 방향 장파 복사 손실 감소 등)은 **아직 검증하지 않았다.**

## 4. 결론

1. **"TiDE가 태양추적에 진 이유" = 예측 오차 (주원인)**
   - case2로 학습해 case3에 적용한 불일치 때문에, 관성과 무관한 PV조차 잘못 예측했다.
2. **사용자 가설(시간 누적 효과)은 사실이다. 다만 크기는 약 1,100 kWh.**
   - 주로 난방에서 발생하며, PV에는 없다.
   - 승패를 가른 원인은 아니고, 정확한 예측 위에 얹을 추가 개선 여지다.
3. **잠재력은 크다.** 완벽한 timestep 예측만으로 태양추적 대비 −2,966 kWh (net −7,624 kWh)가 가능하다.
4. **단순 baseline도 태양추적보다 강하다.** 50° 고정(−5,610), PV 최대화(−6,002). 향후 비교 baseline으로 함께 제시하는 것이 공정하다.

## 6. 재현 방법

```bash
# 고정각 10개 + 태양추적 + TiDE S1/S2 (병렬)
python run_case3_schedule_sim.py --batch data/schedules/phase0_batch.json --jobs 13

# case3 고정각 데이터셋 및 oracle 스케줄 생성

python run_case3_schedule_sim.py --batch data/schedules/phase0_oracle_batch.json --jobs 2
```

참고: `oracle_pvmax.csv`는 세션 중 일회성 분석 코드로 만들었다. 기준은 각 timestep에서 PV 발전량이 최대인 각도이고, 모든 각도가 동률이면 태양추적 각도를 쓴다. 재현이 필요하면 `build_oracle_schedule.py`에 옵션으로 추가할 것.
